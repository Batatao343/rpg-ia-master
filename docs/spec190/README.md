# SPEC-190: conta, recuperação e retenção

## Contrato operacional

- O backend usa Supabase Auth por HTTP e guarda access/refresh apenas em cookies. `GET /auth/config` anuncia confirmação e Turnstile. Signup, reenvio e reset respondem com mensagem genérica; limites de IP e endereço normalizado precedem o envio. Falhas de envio HTTP/SMTP mantêm a resposta 202, mas registram `rpg_auth_email_delivery_failures_total{action,status_class}` e evento de log sem endereço/token. `RPG_AUTH_CAPTCHA_REQUIRED=1` exige site key, secret e validação de hostname/action no servidor; sem configuração, falha fechado.
- `RPG_AUTH_CAPTCHA_MODE=app` mantém a verificação no proxy para testes locais. No hosted público, use `RPG_AUTH_CAPTCHA_MODE=gotrue`, `RPG_AUTH_CAPTCHA_REQUIRED=1`, site key Turnstile e habilite a proteção CAPTCHA nativa no painel Supabase Auth com o secret correspondente. Nesse modo o proxy exige token em signup, login, reset, reenvio e reautenticação, e o envia ainda não consumido em `gotrue_meta_security.captcha_token`; cada tentativa requer token novo. Ausência de modo/required/site key válido bloqueia a operação. Como a API GoTrue hospedada aceita chamadas diretas com publishable key, o CAPTCHA exclusivo do proxy não protege essa superfície pública. O gate de staging da SPEC-191 precisa confirmar diretamente que GoTrue rejeita requisições sem token e que os limites nativos de Auth estão configurados.
- O IP que GoTrue observa nas chamadas do backend é o egress compartilhado do servidor. Preserve o limite próprio do proxy por IP/e-mail e revise os limites nativos por projeto/IP no staging. `Sb-Forwarded-For` só é aceito por GoTrue com secret API key e opt-in explícito do projeto; esta implementação não encaminha esse header nem substitui a publishable key. Planeje esse ajuste separadamente se o egress compartilhado causar bloqueio de usuários legítimos.
- Os templates locais `supabase/templates/confirmation.html` e `recovery.html` enviam `TokenHash` no fragmento `/#auth_action=verify|recovery&token_hash=...`; o hash não vai na requisição HTTP de navegação. O browser submete o hash ao backend após interação. Em hosted, copie os templates para Auth > Email Templates, configure `Site URL` e SMTP; `supabase/config.toml` vale só para a stack local. A confirmação também deve estar habilitada no painel hosted. O backend permanece com `RPG_AUTH_EMAIL_CONFIRMATION_REQUIRED=1`. Supabase informa que projetos Free novos com SMTP padrão não podem personalizar templates; use SMTP próprio ou plano com personalização antes do beta.
- Export e exclusão exigem senha recente da sessão atual. O pedido de exclusão revoga sessões e refresh tokens no primeiro commit, cancela jobs, cria tombstone durável e limpa blobs e tabelas privadas. Triggers bloqueiam escritores tardios, inclusive publicação em `storage.objects` pelo service role. O recibo de exclusão permite apenas repetir `/account/delete` durante sete dias; uma nova sessão de outra conta limpa o recibo. Se o processo cair após revogar a sessão e antes de enviar o recibo, o mesmo cookie de acesso antigo com prova recente válida por cinco minutos pode apenas retomar uma tombstone existente do mesmo owner.
- Antes de finalizar a exclusão, sessões Checkout abertas são expiradas no Stripe test. Uma criação remota em andamento é retomada com a mesma chave de idempotência e fechada. Se Stripe estiver indisponível, dados privados, blobs disponíveis e usuário Auth ainda são apagados; a tombstone permanece `deleting` para nova tentativa de fechamento financeiro. O kill switch `RPG_STRIPE_ENABLED=0` fecha novas vendas, mas cleanup continua usando `STRIPE_SECRET_KEY` e `RPG_CHECKOUT_ORIGIN`; webhook de reconciliação continua usando a chave test e `STRIPE_WEBHOOK_SECRET`, sem exigir SKU ativo. Preserve essas credenciais até encerrar pedidos pendentes. Um webhook `paid` tardio grava `late_paid_after_delete` com `refund_required` na trilha financeira e mantém a ordem em reconciliação, sem conceder Estilhas a uma wallet inacessível.

## Dados após exclusão

| Destino | Dados | Razão técnica |
| --- | --- | --- |
| Removidos | Auth user, sessões, jogos, eventos, turnos, memória vetorial, crônica, operações, jobs, assets, arte, briefs/quotes privados, uso técnico, blobs `users/{owner}/...` | Não são necessários para reconciliação financeira. |
| Retidos | `wallet_accounts`, entradas append-only, reservas, tickets, liquidações, `payment_orders`, `payment_financial_events` e fatos Stripe sanitizados | Preservam trilha de compra/consumo/estorno/disputa e permitem webhook tardio auditável. |
| Controle mínimo | `app.account_deletions` com UUID opaco, estado e timestamps | Nega tokens antigos e impede ressurreição de dados privados. |
| Temporários | Buckets de rate limit por e-mail normalizado são removidos na exclusão; os demais buckets Auth expiram em 24 horas e são purgados pela rotina agendada | SHA-256 de endereço pode ser descoberto por dicionário e não integra a trilha financeira. |

`payment_orders.checkout_url` é limpo e não pode reaparecer por resposta tardia do Checkout. Os fatos Stripe não guardam payload bruto. A wallet retida não autentica o usuário apagado, não libera gameplay nem dispara nova cobrança. Uma confirmação de pagamento ou estorno tardio ainda atualiza a trilha financeira sem ressuscitar conta. O UUID permanece como chave de reconciliação; isso é retenção de dado pseudônimo, não anonimização. Este documento descreve comportamento técnico e **não afirma conformidade legal nem fixa prazo legal**. Prazo, acesso operacional, solicitação de eliminação dos registros financeiros e política de backups dependem de revisão jurídica/financeira antes de produção pública.

## Recuperação de exclusão incompleta

Com ambiente `hosted-supabase` configurado e credenciais de backend:

```text
uv run python -m scripts.recover_account_deletions
uv run python -m scripts.recover_account_deletions --owner <UUID>
uv run python -m scripts.recover_account_deletions --owner <UUID> --apply --confirm-owner <mesmo UUID>
# No scheduler do mesmo ambiente backend, a cada 5 minutos:
RPG_ACCOUNT_RECOVERY_BATCH=1 uv run python -m scripts.recover_account_deletions --batch --apply --max 10
```

Preview lista até 100 pedidos `deleting` e não altera dados. `--apply` só aceita UUID com tombstone existente; retoma a limpeza, retorna `deleted` ou código 2 se Stripe/Storage ainda estiver indisponível. O batch é opt-in por variável do worker, limita cada passagem a dez owners por padrão e usa `recovery_attempted_at` com `SKIP LOCKED`: falhas antigas não impedem pedidos novos. Ele purga buckets Auth com mais de 24 horas e deve ser agendado a cada cinco minutos no ambiente que já hospeda o worker. Não inicia exclusão de uma conta ativa. Não publicar DSN, service key, export ou UUID de clientes em logs/tickets. O scheduler e alertas de exit 2 são condição operacional para o beta; o código sozinho não instala uma agenda cloud. A topologia e a configuração cloud efetiva pertencem à SPEC-192.

## Evidência e limites

Testes determinísticos cobrem transporte Auth, mensagens iguais para endereços existentes/ausentes, CAPTCHA, prova recente, recibo A/B, tombstone, acesso com JWT antigo, RLS, service role Storage e isolamento A/B. Testes locais com PostgreSQL e GoTrue cobrem migração, fluxo real de hash/reset e reconciliação de pagamento/estorno tardios sem chamadas Stripe live. O gate pré-commit fechou com **2.159 passed, 126 skipped, 15 deselected** no Python, **53 passed, 1 skipped** no Chromium com dois workers e **18 passed** no Node; build Vite, Ruff, lint de conteúdo e Project Index fresh. A revisão independente Sol High está **APPROVED** em `handoffs/SPEC-190-SOL-independent-review.md`, sem achado bloqueante. O teste concorrente usa uma conexão PostgreSQL compartilhada e não prova a ordem de locks entre duas sessões independentes; a rotina de recuperação trata abortos transitórios. CAPTCHA/rate limits nativos, SMTP hosted e o scheduler de recuperação ainda exigem configuração e smoke no staging das SPEC-191/192. Não houve Stripe live, cobrança comercial nem recarga de modelo de IA.
