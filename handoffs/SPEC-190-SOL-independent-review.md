## Limits to carry forward

- The two-thread `finish()` test overlaps provider calls but serializes SQL through one test connection (`tests/test_account_lifecycle_financial_local.py:116-171`). It proves idempotent external overlap, not independent PostgreSQL lock ordering. A real two-connection race can abort one transaction on a deadlock because final erasure takes the owner advisory lock before the payment-order row while webhook/Checkout closure takes the row before the owner advisory lock. The tombstone, retry sweep and Stripe webhook redelivery make this recoverable; I found no demonstrated cross-owner write or duplicate credit. Add a two-connection integration test if concurrent deletion throughput becomes a release requirement.
- The recovery CLI is implemented, but the cloud scheduler and alerting are not provisioned by SPEC-190. SPEC-192 requires a five-minute deployment job and alert on unfinished cleanup; SPEC-191 requires hosted Auth CAPTCHA/rate-limit probes. Do not treat this review as evidence that those external gates are configured.
- If Storage is unavailable, its blobs remain until retry; deletion stays `deleting`. The storage publication fence prevents new objects after the tombstone. The retention document correctly distinguishes retained financial facts from private data and leaves legal retention periods for separate review (`docs/spec190/README.md:16-35`).

Recheck this decision if the implementation changes after this snapshot or the full gate fails.
